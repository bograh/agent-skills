# Backend Security Checklist

> Source: [The Copenhagen Book](https://thecopenhagenbook.com) — a community-maintained guide on implementing auth in web applications.

Use this skill to guide security reviews, scaffold new auth systems, or answer "am I doing this right?" questions. Work through the relevant sections and flag any missing items.

---

## 1. Server-Side Tokens (Session IDs, Reset Tokens, etc.)

**Generation**
- [ ] Tokens have at least **112 bits of entropy** (120–256 bits recommended)
- [ ] Generated with a **cryptographically secure** random source (e.g., `crypto/rand`, `secrets` module — NOT `math/rand` or `Math.random()`)
- [ ] Tokens are case-sensitive (or constrained to lowercase if storage is case-insensitive, e.g. MySQL)

**Storage**
- [ ] High-value tokens (password reset, email verify) are **hashed with SHA-256** before storage
- [ ] Single-use tokens are deleted **atomically** on retrieval (use transactions in SQL)
- [ ] Token table has a `expires_at` column and expiry is checked on every use

---

## 2. Sessions

**Session IDs**
- [ ] Session IDs are generated per the [Token rules](#1-server-side-tokens) above
- [ ] Session IDs are optionally hashed before storage for extra security

**Lifetime**
- [ ] Sessions expire automatically (critical apps: short TTL; social apps: ~30 days with sliding window)
- [ ] If using sliding expiration: extend only when within the last 50% of lifetime
- [ ] Absolute session cap is enforced for sensitive applications (e.g., max 12 hours regardless of activity)

**Session Cookies**
- [ ] `HttpOnly` — prevents JS access
- [ ] `SameSite=Lax` (use `Strict` only for highly sensitive apps)
- [ ] `Secure` — HTTPS only
- [ ] `Max-Age` or `Expires` defined (session won't persist without this)
- [ ] `Path=/` — accessible from all routes
- [ ] Cookie expiration is refreshed continuously if sessions are long-lived (browser max: 400 days)

**Invalidation**
- [ ] Session is invalidated on **sign-out**
- [ ] All sessions invalidated on **password change**
- [ ] All sessions invalidated when **permissions change** (e.g., email verified, role updated)
- [ ] For critical apps: all sessions invalidated on any security-sensitive action

**Session Fixation**
- [ ] A **new session is always created** when a user signs in (never reuse a pre-auth session)
- [ ] Session IDs are only accepted via **cookies or headers** — never URL query parameters

**Sudo Mode (Optional but recommended for critical apps)**
- [ ] Track `last_authenticated_at` per session
- [ ] Require re-authentication for sensitive operations if that timestamp is too old

## 3. Password Authentication

**Input Validation**
- [ ] Minimum length: **8 characters**
- [ ] Maximum length: **64–256 characters** (do not silently truncate)
- [ ] All valid Unicode characters permitted, including whitespace
- [ ] Copy-paste is NOT disabled (enables password manager use)
- [ ] Weak password check using a library like `zxcvbn`
- [ ] Compromised password check via [HaveIBeenPwned API](https://haveibeenpwned.com/API/v3) (k-anonymity model — only first 5 chars of SHA-1 hash are sent)

**Password Storage**
- [ ] Passwords are **salted and hashed** — never stored in plain text or with MD5/SHA-1/SHA-256
- [ ] Algorithm priority: **Argon2id** → Scrypt → Bcrypt (legacy)
- [ ] Argon2id minimum params: `memorySize=19456`, `iterations=2`, `parallelism=1`
- [ ] Scrypt minimum params: `N=16384`, `r=16`, `p=1`, `dkLen=64`
- [ ] Bcrypt minimum work factor: **10**
- [ ] Salt is generated by a **cryptographically secure** random generator with ≥120 bits entropy
- [ ] Password comparison uses **constant-time comparison** (e.g., `crypto/subtle.ConstantTimeCompare`)

**Brute-Force Protection**
- [ ] **IP-based rate limiting** implemented (e.g., block for 10 min after 10 failed attempts)
- [ ] Consider **identifier-based throttling** on top of IP throttling
- [ ] Consider **CAPTCHA** for high-risk endpoints
- [ ] MFA offered (or required for critical apps) — best defense against credential stuffing

**Error Messages**
- [ ] Login errors are vague: "Incorrect username or password" — not "Incorrect password"
- [ ] Registration does not confirm whether an email is already taken (if privacy is required)
- [ ] Password reset does not confirm whether an email exists (if privacy is required)
- [ ] Response times are consistent to avoid timing-based user enumeration

**Other**
- [ ] Current password is required when user changes their password
- [ ] Users are NOT forced to change passwords periodically (NIST guidance)

## 4. Email Verification

**Input Validation**
- [ ] Email addresses are normalized to **lowercase** before storage and comparison
- [ ] Validation checks: contains `@`, character before `@`, domain has `.`, no leading/trailing whitespace, max 255 chars
- [ ] Avoid complex Regex (ReDoS risk) — use simple structural checks

**Verification Codes**
- [ ] Code is ≥8 digits (numeric) or ≥6 characters (alphanumeric)
- [ ] Ambiguous characters excluded (0, O, 1, I)
- [ ] Generated with a cryptographically secure random generator
- [ ] Single-use: invalidated immediately after first use
- [ ] Tied to a specific user **and** email address
- [ ] Valid for 1–24 hours (generate new if expired, not if still valid and within window)
- [ ] Rate-limited by user ID (~10 attempts per hour)
- [ ] **All sessions invalidated** when email is verified (create a new one for the current user)

**Verification Links**
- [ ] Token meets [Server-Side Token rules](#1-server-side-tokens)
- [ ] Single-use: deleted immediately after use
- [ ] `Referrer-Policy: strict-origin` set on any page that includes tokens in the URL
- [ ] **All sessions invalidated** when email is verified

**Changing Emails**
- [ ] Password (or MFA second factor) required before changing email
- [ ] New email stored separately until verified
- [ ] Notification sent to the **previous** email address

**Rate Limiting**
- [ ] All email-sending endpoints are **strictly rate-limited**

## 5. Password Reset

**Flow**
- [ ] Reset links use a secure random [token](#1-server-side-tokens)
- [ ] Tokens valid for ~1 hour (max 24 hours)
- [ ] Token is **single-use**: deleted immediately after a valid new password is submitted
- [ ] Existing tokens invalidated when a new reset is requested (or reuse the existing valid one)
- [ ] Tokens hashed with SHA-256 before storage
- [ ] `Referrer-Policy: strict-origin` set on the reset page
- [ ] **All sessions invalidated** after successful password reset
- [ ] Email marked as **verified** after successful reset

**MFA**
- [ ] If user has MFA enabled, second factor is required **before** entering new password

**Error Handling**
- [ ] Reset form response is vague if email privacy is required ("We'll send a reset link if that account exists")

**Rate Limiting**
- [ ] Reset email endpoint is **strictly rate-limited** (consider CAPTCHA)

## 6. OAuth 2.0

**Authorization Request**
- [ ] `state` parameter generated per request using a cryptographically secure random generator (≥112 bits entropy)
- [ ] State stored in a `HttpOnly`, `SameSite=Lax`, `Secure`, `Path=/` cookie (or in session)
- [ ] PKCE (`code_challenge` / `code_verifier`) used if provider supports it
- [ ] Code verifier: ≥112 bits entropy, stored same as state
- [ ] Implicit grant type is **NOT** used (it is deprecated)

**Callback Validation**
- [ ] `state` parameter **presence is verified** before comparing (common mistake: assuming it exists)
- [ ] State from callback matches stored state — return error if missing or mismatched
- [ ] Authorization code exchanged via **server-side POST** request, never client-side
- [ ] Client secret kept server-side, never exposed to the browser
- [ ] Access token is **never** used as a session replacement — create a proper server session

**Account Linking**
- [ ] If linking by email: verify that the provider explicitly marks the email as **verified**
- [ ] Block users with unverified OAuth emails from completing auth

## 7. Multi-Factor Authentication (MFA)

**TOTP**
- [ ] TOTP secret is exactly **160 bits**, generated with a cryptographically secure generator
- [ ] Each user has a **unique** secret
- [ ] QR code registration confirmed: user must verify OTP before TOTP is activated
- [ ] Generating a new QR code **invalidates** the previous secret
- [ ] TOTP validation is **rate-limited** (block for 15–60 min after 5 consecutive failures)
- [ ] User notified to change password after TOTP failures

**SMS (Discouraged)**
- [ ] If used, codes follow email verification code guidance (valid ~5 min)
- [ ] Rate-limited same as TOTP

**Recovery Codes**
- [ ] At least one recovery code issued per user
- [ ] Generated with cryptographically secure generator (≥40 bits / ~10 hex chars)
- [ ] **Single-use**: deleted after use
- [ ] Hashed with Argon2id (or equivalent) before storage
- [ ] Only shown once (at registration time)
- [ ] User can regenerate if they have access to their second factor

## 8. CSRF Protection

**General Rules**
- [ ] CSRF protection implemented for **all state-mutating routes** (POST, PUT, DELETE, PATCH)
- [ ] GET requests do **not** modify resources (critical if relying on `SameSite=Lax`)
- [ ] CORS policy is strict — `Access-Control-Allow-Credentials` is not loosely set

**Preferred Methods (choose one or combine)**

*Origin Header Check (simplest):*
- [ ] `Origin` header verified against expected domain for all non-GET requests
- [ ] Request rejected if `Origin` header is absent
- [ ] `Referer` header used as fallback if `Origin` is absent

*Anti-CSRF Token:*
- [ ] Unique CSRF token per session stored server-side
- [ ] Token included in every mutating form as a hidden field
- [ ] Token is **not** single-use per form submission (would break back button)

*Signed Double-Submit Cookie:*
- [ ] Token signed with HMAC-SHA-256 using a server secret
- [ ] HMAC is **tied to the user's session ID** (prevents subdomain injection)
- [ ] Cookie has `Secure`, `HttpOnly`, and `SameSite` attributes

**SameSite Cookie**
- [ ] Session cookie has `SameSite=Lax` (minimum)
- [ ] `SameSite` alone is NOT considered sufficient — combine with one of the methods above

---

## 9. Open Redirect Prevention

- [ ] Any redirect destination provided by users is **validated against an allowlist** of internal paths
- [ ] External URLs are **never** accepted as redirect targets without explicit allowlisting
- [ ] `redirect_to` parameters are restricted to **relative paths** (not absolute URLs)

---

## 10. Random Value Generation

- [ ] All security-sensitive random values use a **cryptographically secure** generator:
  - Go: `crypto/rand`
  - Node.js: `crypto.randomBytes()`
  - Python: `secrets` module
  - Java: `SecureRandom`
- [ ] Standard math/pseudo-random functions (`Math.random()`, `rand()`) are **never** used for tokens, salts, or secrets

## Quick Reference: Entropy Minimums

| Use Case | Minimum Entropy |
|---|---|
| Session IDs | 112 bits |
| OAuth state / PKCE verifier | 112 bits |
| Email / password reset tokens | 112 bits |
| TOTP secret | 160 bits (exactly) |
| MFA recovery codes | 40 bits |
| Password salt | 120 bits |
